# Implement one locked Wand Night Stand screen

Start with [PRODUCT.md](../../../PRODUCT.md) for current language, comedy and
Responsive Table direction. Historical screen records cannot override it.

Use this skill only when asked to implement or update a specific approved smartphone screen. An approved direction does not grant scope to implement every approved screen. Keep the selected target; do not restart multi-option ideation. If a missing product decision or constraint would materially change UX, isolate it and continue independent authorized work.

1. Resolve the requested screen ID and latest approved local reference/specification in [`design-system/consumer-game-ui.md`](../../../design-system/consumer-game-ui.md). Read that specification, the guide and only affected source.
2. Reuse existing scene components, semantic tokens, actions and production art. Identify the smallest real delta before editing. Keep authorization, identity, consent, generation and server state in their existing feature owners.
3. Implement only the requested screen and its necessary loading, error, offline, consent, cancellation and recovery states. Preserve mobile safe areas, keyboard behavior, themes, reduced motion and live status semantics.
4. Render the actual application at the required mobile size. Compare it with the selected local reference, inspect focus and key interactions, then refine concrete defects.
5. Run proportionate behavioral, visual and accessibility checks. Distinguish browser evidence from native passkey/device evidence.
6. Update that screen's implementation status and exact verification evidence in the canonical guide; list remaining gaps. Design approval, implementation and verification are separate statuses.

When a requested screen lacks a concrete specification, record its purpose, states, mobile layout and validation in the guide. Keep public repository content free of private design-space URLs, invitation secrets and real guest data.
